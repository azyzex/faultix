Faultix — v0.2.1

Your build broke.
Here is the brief.

A local-first VS Code extension that watches for failing commands, works out the root cause, and writes a brief you can hand straight to a coding agent. No network calls, no telemetry.

Method

Eight stages, in order

Each stage feeds the next, so the numbering is the actual execution order rather than a label. Everything from sanitize to render is pure and free of VS Code APIs, which is what makes it testable without launching an editor.

  1. sanitize
    Strip ANSI colour, cursor movement, device-status queries, window titles and shell-integration markers. Collapse progress bars back to their final line.
  2. redact
    Remove tokens, keys, passwords and URL credentials before anything is persisted. Twenty patterns, each with bounded quantifiers.
  3. classify
    Decide what kind of failure this is and which toolchain produced it. The tool hint selects which parser gets first pick at the text.
  4. extract
    Parse structured error records with per-toolchain matchers ranked by confidence, then pick the one that actually stopped the build.
  5. resolve
    Turn every printed path — absolute, relative, ./-prefixed, Windows or POSIX — into one canonical file inside the workspace.
  6. rank
    Score the files worth opening first, weighing evidence by how directly the failure implicated it.
  7. context
    Read the lines around each failure location so the brief carries the code, not just a reference to it.
  8. fingerprint
    Hash the normalized command and primary error, so the same failure is recognised across runs and a brief can say “seen six times”.
Design

The interesting decision

Ranking suspects is where a tool like this earns its keep or becomes noise. The rule that matters is corroboration.

The failure mode

A workspace routinely has hundreds of open editor warnings that have nothing to do with the command that just failed. Counting them as evidence meant a warning-heavy config file could rank second for a failing shell script — confidently pointing at the wrong file.

The rule

Diagnostics count fully only when the failure output names the same file. A file known only from ambient diagnostics is not listed at all. When there is no output to corroborate against, they become the primary signal instead.

Weighting

Named by the primary error scores highest, then command arguments, then parsed errors with a decay down the list, then plain mentions. Vendored and generated paths are multiplied down rather than filtered, so they can still surface when nothing else does.

Precision over recall

Three good suspects beat fifteen plausible ones. An agent acts on what it is handed, so a confident wrong answer costs more than a short one.

Coverage

Verified against real output

Root-cause extraction is tested against twenty-three recorded captures from sixteen toolchains — real stdout and stderr, escape bytes and all, not hand-written approximations. Adding a toolchain means recording a fixture and stating what the root cause should be.

Findings

What the tests caught

Bugs the suite found in code that looked correct — the argument for fixture-driven tests over mocks.

  • ▪ The primary error appeared twice in every agent prompt: de-duplication compared object identity, which never held because the two records were built separately.
  • ▪ Anonymizing home directories before analysis turned every stack frame into an unresolvable <home>\…, silently disabling code snippets and open-at-line. It now runs at render time.
  • ▪ Treating bin as build output demoted real Rust sources in src/bin.
  • ▪ expect(x).toBe(5) parsed as the file .toBe at line 5.
  • ▪ A task named “Run unit tests” did not classify as a test, because the pattern only matched the singular.
  • ▪ Every capture was recorded twice, so repeat counts advanced in steps of two. The integration test asserted “at least 2” and passed anyway; it now measures an exact delta and was checked to fail when the bug is reintroduced.
  • ▪ engines.vscode claimed ^1.88 while the extension depends on an API finalized in 1.93, because @types/vscode was allowed to float twenty minors past the declared floor.
Security

Three things worth being careful about

Output contains secrets

Failing commands print credentials: a CI token echoed by a script, a database URL in a connection error. Twenty redaction patterns run before anything is written, and each brief reports how much it removed.

Settings are untrusted

A workspace carries its own settings.json, so the output directory is resolved against the workspace root and refused if it escapes — absolute, drive-qualified, UNC and .. alike. Asserted against the filesystem, not mocked.

Output is attacker-influenced

Lines are capped at 2,000 characters and 5,000 lines before matching, and every pattern uses bounded quantifiers, so no input can trigger catastrophic backtracking in the editor process.

What it never does

No network calls and no telemetry — there is no HTTP client. The only subprocess is git, with a fixed argument array and a 1.5 second timeout.
